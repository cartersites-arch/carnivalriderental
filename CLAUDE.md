# Instructions for future sessions

Read `docs/PROJECT_BRIEF.md` first. It is the business model; do not drift from it.

- BUSINESS MODEL (founder decision 2026-10-06, `docs/PROJECT_BRIEF.md`): Carnival Ride Rental is a national carnival ride **discovery and operator-access platform**. Visitors browse inventory for free; customers buy **Event Access** (contact details for matching independent operators) through our own standard Stripe account; the rental itself happens directly between customer and operator. We never collect rental payments, pay operators, charge commission, or guarantee bookings or availability. **Do not reintroduce Stripe Connect, marketplace checkout, booking transactions, operator payouts, or a mirror of the Sharetribe catalog without a new founder decision.**
- SHARETRIBE'S ROLE (`docs/PAID_ACCESS_ARCHITECTURE.md`): catalog and operator-management infrastructure only: operator accounts, claims, listings, fields, photos, approval, and the private contact record. Its transaction and payment layer is unused. The operator listing type is Free messaging (`default-inquiry`); operators never need payout details. The only other durable store is the access ledger (Postgres via `src/lib/access`), which holds purchases, passes, unlocks and audit, and references Sharetribe IDs. Never copy listings into it.
- LOCKED DATA: operator identity and contact (company name where identifying, contact person, phone, email, website, exact address) is revealed only by the server after an entitlement check (`src/lib/access`). It must never appear in HTML, hydration data, JSON-LD, metadata, Open Graph, alt text, API responses, static exports, the inventory snapshot, sitemaps, analytics or logs. Pass and connect pages are `private, no-store` and noindex. `tests/privacy-*.test.ts` and `e2e/privacy.spec.ts` guard this; do not weaken them.
- PUBLIC DATA: ride, class, photo, verified facts, home state, approximate distance, service states, event fit, related rides. Never invent specs, capacities, reviews, ratings, supplier counts, availability, rental prices, insurance or certification claims. Unknown stays `null`.
- EVENT ACCESS RULES (`src/lib/access`): price, unlock limit, validity and the minimum contactable matches live in `access_products`, never in copy (public copy reads them through `accessProductsForDisplay()` / `lib/access/copy.ts`). Two tiers (founder decision 2026-10-12): `event-access` ($99) and `ferris-wheel-access` ($199, any Ferris wheel variant). The tier comes only from `pricing.ts` → `resolveCriteria` (authoritative listing classification first, then the canonical ride type), which is the same resolution matching uses; never from a client price, product id, hidden field, referrer or URL. A tier whose product is missing or inactive is not sold (no fallback to another tier). Purchases snapshot product and terms; refunds are judged against the purchased amount. Access is per operator, not per listing. Uncontactable operators are never sold. Payment is server-verified (webhook or server-side Checkout session retrieval); idempotent on Stripe event id; unlock counting is concurrency-safe; refunds and disputes revoke passes but keep the audit. No real charges until the founder sets live Stripe keys; `STRIPE_SECRET_KEY` must belong to the Carnival Ride Rental account, never Pool Rental Near Me's.
- This repo is separate from Pool Rental Near Me. Never touch PRNM code, infrastructure, its Sharetribe marketplace, Stripe account, Supabase project or any other business.
- Build every URL with `paths.*` in `src/lib/seo/routes.ts`. Existing canonical URLs never change; redirects are added centrally in `next.config.ts`.
- Indexing stays gated: `PSEO_INVENTORY.copyApproved`, the pilot allowlist, the near-duplicate gate (`index-eligible.json`), `PUBLIC_INDEXING` and `APP_ENV`. A monetisation change never authorises indexing. See `docs/PSEO_INDEXING_PLAN.md`.
- Listing data follows `contract/operator-listing-contract.json` (operator inventory) and `contract/listing-contract.json` (legacy managed catalog). Never invent field IDs/options in components; every listing write goes through the import scripts' validators; every listing read goes through `src/lib/catalog` or the inventory snapshot. Verify config with `npm run sharetribe:inspect && npm run contract:diff`; UNVERIFIED is never a pass. Configuration changes happen in the Sharetribe **Test** environment and are copied to Live.
- Operator identity on Sharetribe's public surfaces: the Marketplace API serves user and listing `publicData` and `metadata` to anonymous clients, and our catalog depends on those anonymous reads, so **"Make marketplace private" stays OFF** (it returns 403 and empties the catalog). Protection lives in the data: imported accounts and listings are anonymous from the create call (`buildAnonymousPayload`, `buildAnonymousListingPayload`; operator placeholder profile, no company slug or import id in public metadata, identity and phone in `privateData`), and the claim script never restores the company name, bio or website to public fields. `npm run migrate:live -- verify` reads Live as an anonymous visitor and fails on any leak.
- Inventory ingestion is first-class: company accounts via `npm run import:companies` (`docs/COMPANY_IMPORT.md`), listings via `npm run import:listings` (`docs/LISTING_IMPORT.md`), photos via `npm run import:photos` (provenance recorded, removed on request), anonymisation via `npm run ops:anonymize`, claims via `npm run ops:claim`. Keep deduplication, provenance and validation (`npm run inventory:validate`) intact. No mass imports or outreach without a founder go.
- Demo fixtures live only in `src/lib/content/demo/`; publishable records only in `src/lib/content/published/`. Don't weaken `integrity.ts` or `publication.ts` gates.
- Email goes through `src/lib/email` (`docs/EMAIL.md`). `EMAIL_MODE` stays `test` (everything to qa@) until the founder flips it. Outreach needs an approved campaign, unsubscribe, suppression and a real postal address.
- Secrets live in `.env.local` (gitignored) and Vercel env. Never commit or log them. The Integration API secret and Stripe secret are server-only.

Checks before pushing: `npm run typecheck && npm test && npm run build && npm run inventory:validate && npm run pseo:report && npm run pseo:duplicates && npm run test:e2e`.

Production runs on the Sharetribe **Live** marketplace "CarnivalRental" since 2026-10-14 (`docs/SHARETRIBE_LIVE_CUTOVER.md`). Live credentials live under `SHARETRIBE_LIVE_*` in `.env.local`; scripts select Live only with `--target live` and assert the marketplace name before writing.
